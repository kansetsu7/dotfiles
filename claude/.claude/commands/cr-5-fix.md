Execute fixes from `.claude/fix-plan.md`. The plan is normally worked through
**partially** — a group or two per run, not the whole thing.

## Prerequisites

- `.claude/fix-plan.md` must exist (generated by `/cr-4-plan`)
- `.claude/code-review.md` — only needed as background when the plan's **Plan**
  field is thin or points at the reviewer's Notes
- "Needs Decision" / "Design Decisions Needed" items **inside the requested
  scope** must be resolved before starting

## Workflow

### Step 1: Read the plan and settle the scope

1. Read `.claude/fix-plan.md`
2. Determine the scope from `$ARGUMENTS`:
   - Group numbers (`1-3`, `2`) → those groups, in order
   - Item ids (`🟡 #9`, `#9`) → those items only
   - `all` → every group, in order
   - **Empty → do not guess.** List the groups with their todo status
     (`Group 4: Controller flash + naming pass — 0/6 todos`) and ask which to run
3. Check the requested scope only:
   - Unresolved "Needs Decision" / "Design Decisions Needed" items → list them
     and ask the user to resolve first
   - Items whose dependencies sit in an earlier, unfinished group → say so and
     ask whether to pull those in
4. Restate the scope before touching code: the items, the order, and how many
   commits it will produce. For the first item, offer the commit subject/message
   so the user can confirm the framing early.

### Step 2: Process each item

For each item in scope with unchecked `[ ]` todos:

a. **Follow the item's Plan.** `/cr-4-plan` always records **Approach** and
   **Plan**, and the Plan already reflects the chosen approach (Suggested fix or
   the reviewer's Alternative). Read `.claude/code-review.md` only when the Plan
   is ambiguous, cites Notes you cannot see, or looks wrong.

b. **Answer open questions first.** If the Plan or Side effects contain a
   question (`?`), answer it with reasoning before writing code.

c. **Implement:**
   - Work the **Todo** checklist in order; mark each `[x]` in `fix-plan.md` as
     you go
   - Also apply the item's **Side effects** (test updates, comment rewordings,
     call-site changes) — they are part of the item, not optional
   - Verify: run the tests named in the plan's "Tests to re-run", plus lint.
     Capture the **baseline** failures on the pre-change commit first if the
     suite is not green, so you can prove you introduced nothing new

d. **Commit** (see Commit convention below) — one commit per item.

e. **Report:**
   ```
   Fixed: `<file_path:line>` - <brief title>
   Approach: <one line>
   Commit: <sha> <subject>
   ```

### Step 3: Skip non-accepted items

Items in the Skipped table (Drop / Won't Fix) and items whose todos are already
`[x]`: skip silently.

### Step 4: Summary

Scope the report to what was actually run:

```markdown
## Fix Summary — <scope>

| Commit | Item |
|---|---|
| `<sha>` | <subject> |

**Files touched:** <paths>
**Tests:** <what was run, baseline vs. after>
**Deviations:** <anything implemented differently from the plan, and why>
**Left in scope:** <items/todos not done, and why>
```

## Commit convention

The project commit style lives in `~/.claude/CLAUDE.md` (Background / Problem /
Approach). On top of it:

- **One commit per plan item**, in group order. Two items that rewrite the same
  block can still be two commits if the second applies cleanly on top.
- **Stage the `fix-plan.md` checkbox updates with the item's own commit** — the
  ticked todos belong to the change they describe.
- **Never name review artifacts in a code commit.** No `Group 2`, no `🟡 #10`,
  no "per the fix plan / code review item". `.claude/code-review.md` and
  `.claude/fix-plan.md` are deleted before the MR, so those references become
  dangling. Describe the problem on its own terms and cite real commits (`MR!`,
  short shas) instead.
- **Plan-only commits are the exception.** When a decision changes (an item is
  dropped or re-opened) and only `fix-plan.md` moves, commit that separately —
  there, item numbers are the subject matter and belong in the message.
- Do not mark anything in `.claude/code-review.md`; `fix-plan.md` is the single
  source of progress.

## Important Notes

- **Follow group order** — groups encode dependency ordering
- **When the plan does not survive contact with the code, stop.** If the stated
  approach turns out to be impossible, or only works by touching shared/core
  code outside the item's scope, do not invent a bigger change: report what you
  found, list the options with trade-offs, and let the user choose (Won't Fix is
  a legitimate outcome)
- **A changed decision has knock-ons.** When an item is dropped or re-opened
  mid-flight, grep the plan for references to it (`#N`), fix the Skipped table,
  the group preambles, the Design Decisions section and any side-effect notes
  that cited it — other items are often skipped *because of* that item
- **Rewriting local history is fine** while the branch is unpushed: if an
  abandoned item already landed, rewrite it out rather than adding a revert
  commit, and keep a temporary backup ref while doing so
- **Cascading fixes**: if the plan says an item resolves others, tick their
  todos too and say so in the report
